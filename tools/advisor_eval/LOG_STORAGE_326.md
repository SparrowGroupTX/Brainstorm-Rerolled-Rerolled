# Observation log storage and persistent status — release 326

The user reported a disappearing byte-limit popup after a normal restart while idle at the title screen. A bounded metadata-only inspection found 53 files totaling 134,216,592 bytes across the public `advisor_player_log_v1` and `advisor_player_log_v2` directories. That left 1,136 bytes below the prior 128 MiB total allowance. This establishes a nearly exhausted storage allowance; the popup text itself was not captured, no log contents were decoded, and the restart report does not attest loaded version or module hashes. The inspection receipt is `development326/storage_metadata.json`.

The user explicitly selected a 1 GiB allowance and then requested deletion of all previous logs. The targeted cleanup removed those 53 public observation files, totaling 134,216,592 bytes, and verified both directories empty at completion. `development326/log_cleanup.json` records the exact scope and file receipts. These external log originals are deleted, not preserved. Existing repository audits and historical experiment evidence remain; saves, checkpoints, profiles, settings and repository work were outside the cleanup. This one-time user authorization does not introduce automatic deletion or grant broader cleanup authority.

Both the archive and legacy journal allowance are now 1,073,741,824 bytes, exactly 1 GiB. The archive continues counting existing v1 and v2 observations together. Per-event, segment, file-count and session limits remain intact; exhausting any applicable limit still stops recording with an explicit error. Increasing disk capacity does not renew a search request, auto-run limit, retry count or historical experiment allowance.

The Advisor settings page adds a persistent **Recording status** control. Its detail view shows bounded, paginated status and errors so a short-lived alert is no longer the only way to inspect a recording failure. Full status also carries the recording error. The popup points to the persistent view. Text bounds retain complete UTF-8 characters. A writer's sticky error is not automatically cleared because files were deleted; a normal restart loads the new code and creates a fresh writer. No running game was restarted or controlled through tools.

Periodic performance-summary flushing waits while the game is positively identified as idle at `MAIN_MENU` and no active/busy/resuming auto-run or native/legacy search is underway. The existing bounded in-memory timing window is retained rather than repeatedly written while idle; its elapsed duration still includes the idle interval when activity resumes. Explicit action logging remains unchanged, as do timing failure handling and the fixed limits on diagnostic records. Unknown stage or active work does not qualify for this idle suppression. This change does not establish a live CPU reduction, remove a measured freeze cause or guarantee a particular logging duration.
