# Optional fresh synthetic Gold objective for a prospective source attempt

This is an unexecuted source-adapter draft, not a runtime release. It does not alter C01/C02 or the shared adapter. No executable ZIP or player file was read for this work, and no source worker was launched.

For a fresh registered adapter directory, first copy the existing complete `development299/normal_adapter` baseline, then replace `engine_probe.py` and `engine_run.lua` with these changed copies and add `gold_objective_spec.py` and `gold_objective_context.lua`. For API9 recipes, independently include the reviewed `development300/search05/normal_recipe.py` replacement. Freeze every complete adapter file, the new helpers, exact policy/source/runtime/profile/selection/recipe provenance, and a one-use job before execution. The draft-generation script is read/copy tooling only and should not be rerun over its existing outputs.

The added CLI option defaults to `--gold-objective off`. C01/C02's disabled context remains historical evidence; adding this option does not reinterpret them. A new attempt can explicitly pass `--gold-objective synthetic_fresh_all_missing_v1` only with a normal filtered Red/Zodiac Gold episode, `all_unlocked_discovered_v1`, disclosed external selected-seed evidence and its frozen recipe. Replays, source scenarios, profile-only mode, challenge routes and partial player missing lists are rejected before the source ZIP is opened.

Python adds the explicit specification and digest to provenance whether enabled or off. Both new helper hashes enter the complete adapter digest. Lua loads the frozen policy's `gold_goal` module only when the option is enabled and attaches context after ordinary filtered startup sets `seeded=false`, before any advisor decision. The new `engine_gold_objective_context` receipt records the actual initial loaded capture and verifies natural empty Joker history separately from the option declaration.

The enabled context reads the original source's already-loaded synthetic profile. It requires naturally empty `joker_usage`; it does not insert invented wins or replace existing history. The actual frozen `gold_stickers.capture` must classify all 150 vanilla records as missing with zero unknown, validate original stake/catalog/inventory metadata and consider the initial run eligible. Missing or modified metadata fails with an explicit `HEADLESS_BOUNDARY`; the helper never fills it in. The existing original source callbacks alone can later create actual in-memory acquisition/loss/win rows.

The snapshot decorator follows the product's existing `completionist_goal` field and reruns the actual product capture each time. Buying/holding a Joker remains missing. Profile or GAME table replacement, including a same-id profile replacement, fails before another decision. Unknown/malformed metadata also fails instead of silently disabling collection credit. Actual terminal capture may be ineligible because the run is already won; its actual newly recorded Gold counters remain observable. No action, original callback, score cap, random sampler or native search is overridden by this context.

The source adapter currently initializes original item prototypes and then original `G:load_profile(1)` through its existing in-memory-only storage boundaries. This should supply vanilla `P_STAKES`/stake pool and `sticker_map` to the frozen capture. That is an implementation expectation, not a new source qualification result: this draft has not yet exercised those live source metadata surfaces. In particular, do not manufacture a lowercase/uppercase sticker map or empty table to make qualification pass.

Pure validation passed **6 Python tests (with rejection subcases)** and **37 Lua checks**. The Lua fixture uses the actual repository Gold capture and Gold objective modules with declared fake vanilla catalogs/profile data. It verifies default-off no-read behavior, all-150-missing initialization, nonmutation, held-versus-awarded distinction, actual changed-counter reread, preserved initial receipt, unknown/stale metadata rejection and required actual Gold-policy wiring. Python tests parse the changed adapter and verify explicit mode, restrictions, pre-source validation and provenance/pre-decision integration. These fixtures establish adapter plumbing only, not original-source behavior or a completed collection run.

The current Gold objective policy is deliberately narrow: its complete cargo comparison requires a supported final pre-boss shop and stable supported Joker effects. Enabling context does not force a purchase, guarantee retention, expand supported bosses, ensure Perkeo is retained or prove faster achievement completion. Future source traces should report each admitted/rejected cargo comparison and the original terminal held-Joker increments separately.
