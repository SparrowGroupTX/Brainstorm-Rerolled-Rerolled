# Explicit-start product auto-run facade

Stage `auto_terminal.lua` and `auto_run_product.lua` to `Brainstorm/Core/`; stage the two `advisor_auto_*.lua` fixtures to `tests/` and change their three draft `dofile` paths to deployed module paths. The separate pure controller goes to `Brainstorm/Advisor/auto_run.lua`.

After Advisor, checkpoint and collection-search initialization, load the controller and terminal modules and call `product.attach(Brainstorm,{controller=controller,terminal=terminal})`. The facade is `Brainstorm.AutoRun`. Its public methods use colons: `:start(options)`, `:stop(reason)`, `:manual(reason,kind)`, `:update()`, `:status()`, `:owned()`. It publishes `status_text`. The native collection facade retains its existing dot API.

Only an explicit product Start click calls `:start`. Flat UI options `deck_name`, `interchangeable_copies`, `minimum_distinct`, `first_ante`, `last_ante`, `budget_ms` are copied into the pure controller's `search_request`; explicit false survives. Nested `search_request` is also accepted, with conflicting duplicate fields rejected. Start enables normal-deck advice, the Gold objective and bounded player recording, logs that consent, closes the current menu through the original callback, then waits for a separate settled update. No search or gameplay runs inside Start. Nothing persists the active session or resumes it after a restart.

Call `:manual` for physical keyboard/mouse input, checkpoint save/load and settings/profile changes. Internal product actions have narrowly scoped ownership so their synchronous callbacks do not stop themselves. Existing Advisor Execute guards remain authoritative. Around only `A.execute`, `player_log.source` becomes `auto_run`; it and the ownership depth restore even if the callback throws. A logging failure stops additional work. The journal retains its existing session/storage bounds; auto-run does not renew them.

The facade retains the original native found receipt object across the pure controller's immutable copies. Only an owned matching receipt can launch. An uncertain native begin is cancelled and drained; an absent handle is declared drained only when the product's busy flag and runtime busy function both confirm no remaining worker. No extra search starts during draining.

## Terminal and result UI provenance

The monitor arms a particular actual `G.GAME` table, loaded profile table and profile id only after this controller starts a new run. A table replacement, even with the same profile id, invalidates the binding. `GAME_OVER` takes precedence. A win requires authentic final-boss context, ordinary unseeded Gold stake, ordered original `set_joker_win` then `set_deck_win` positive loaded counter changes, and either the actual threshold or an observed same-round original saved callback. `GAME.won` alone cannot qualify. It never writes profile data itself.

Preserved M02 `state_events_source_references.json` (member `functions/state_events.lua`, SHA256 `6c86aefb42d0323d737f87aaa84f53e42b755e72cd0bfd163b7d9cca5c0a99a9`) shows `win_game` performs accounting and queues the UI in a later immediate event. The monitor binds the later original `create_UIBox_win` definition object to that verified win, consumes its exact identity at `G.FUNCS.overlay_menu`, and remembers only that resulting overlay. A matching UI id alone is insufficient. Its actual result surface must have appeared before a new search can begin.

M11's preserved `inspection/update_game_over.lua` is the complete source `game.lua` lines 3581–3626, full method hash `9ebcb600dab8f462386e6e77a498f9976cc48d280eaba21591d1ff541022dd5d`. It creates the loss overlay synchronously within `Game:update_game_over`. The monitor captures only that original method's newly created overlay for the armed GAME_OVER state. The repeated no-op update cannot adopt an unrelated menu.

M11's `inspection/exit_overlay_menu.lua` is the complete original function, hash `46a9e22a79485b357bbb471bc2332391e787ec4e2f12e39811cb0aa612b4565f`. The facade dismisses only its bound result overlay, on an update after the terminal log, through this original callback. Both controller frame locks must clear before another search/run. It never closes an arbitrary later menu. M11 did not locate global `win_game` in the two searched members; the earlier M02 state-events evidence supplies that method.

Validation: two ordinary synthetic fixtures pass 30 terminal and 73 product checks. They cover asynchronous win UI, exact definition identity, one-use overlay ownership, GAME_OVER precedence, loss continuation after frame locks clear, same-id profile replacement, immutable flat UI forwarding, original native receipt identity, cancellation draining, logging failure, action-source restoration on throw and fresh-action duplicate suppression. These tests do not demonstrate live UI performance or autonomous player achievement completion. No game process or player files were accessed for them.
